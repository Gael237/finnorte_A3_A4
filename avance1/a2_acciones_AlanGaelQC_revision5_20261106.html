Responsable: Alan Gael Quintanilla Clemente · Etapa 3: acciones · GitHub: AlanGaelQC.

Alcance e implementación

La etapa recibe señales y severidad; propone acciones concretas con runbooks recuperados rb-02–rb-08 y devuelve faltantes cuando no hay sustento. rb-01 es solo catálogo de severidad. v2 define faltantes: list[str]; v1 mantiene faltantes: str, por lo que el flujo usa adaptador.

El prompt v2 pide runbook recuperado; validar_acciones(datos, previas) comprueba severidad, IDs permitidos, coincidencia general con señales estructuradas, descripción mínima y patrones destructivos. No recibe el log original ni verifica que 5xx/latencia empeoraran frente a un baseline: no certifica la seguridad semántica de una reversa rb-08.

Prompt v1 y validación

v1 usa rol SRE, restricciones técnicas, IDs permitidos y salida JSON. Ejemplo literal: «Jamás propongas acciones destructivas como “reiniciar todo”, “apagar” o “borrar”»; el JSON pide acciones y faltantes como texto. v2 añade la exigencia de evidencia observada y de un runbook recuperado para cada acción; faltantes pasa a lista.

La regla de código rechaza IDs no autorizados, acciones vagas o destructivas y runbooks sin respaldo en las señales; se valida fuera del prompt para que un texto persuasivo no pueda saltarsela. En la matriz de tres repeticiones validar_acciones pasó 3/3. En la comparación posterior de inc-01-pool, la salida v1 sí disparó el validador: acciones[4] citó rb-02 y acciones[5] citó rb-05 sin respaldo en las señales. La salida v2 pasó el mismo validador. La evidencia completa se verificó y está incluida en este paquete como bitacora/a2_acciones_v1_v2_1x1_20261106.json.
